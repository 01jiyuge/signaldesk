# V0.4.1 · 可靠性与运行边界

日期：2026-10-22。版本：**0.4.1**。延续 [V0.4 的 Sandbox 与 A2A 能力](./V0.4_UPGRADE.md)，本轮完善重试、状态转换、关闭收尾和请求体保护。

## 1. A2A 重试与状态一致性

相同 `message_id` 和相同命令已有确认的远端 Task 映射时，重试直接复用持久化的本地委托记录，不再次向远端发送创建任务的 `POST`。需要最新状态时，使用委托查询接口。同一消息的目标或命令冲突会被拒绝。

终态写入受项目范围的数据库与进程内串行保护。已经记录的完成、失败、取消或拒绝状态，不会被迟到的查询、创建或取消响应覆盖；响应中的远端 Task ID 也必须与已有映射一致。

远端已接受任务、ACK 尚未到达本地时，仍可能留下 `PENDING` 且没有远端 Task ID。本地历史会保留该登记；控制台明确显示尚未确认，不持续请求远端任务状态。此时应核对登记并显式重试原请求，避免用新消息创建重复任务。跨实例网络故障下的外部恰好一次执行，仍依赖远端的幂等行为。

## 2. 取消、恢复与应用生命周期

同一个研究 run 的取消与恢复操作串行执行。取消先等待研究任务停止，再保存取消状态；恢复若无法提交执行器，会回滚入队前的状态。

已创建的状态变更由独立任务持有。请求协程被取消时，服务仍等待该操作完成状态写入与收尾，再向调用方传播取消。关闭服务会停止接收新操作，等待已持有的状态变更，并取消、等待研究任务完成最终写入后再释放存储资源。服务停止产生的可恢复研究保留 `interrupted` 状态。

普通 API 和 A2A 首次创建也覆盖数据库提交、worker 注册及提交失败落库，避免请求断开后留下无人执行的 `queued` 任务。A2A 等待结果的长轮询放在状态操作之外，关闭服务无需等待该轮询超时。AG-UI 等待研究 worker 和取消/恢复操作的最终事件写入后，才发送结束事件与最终游标。

应用资源在初始化前注册关闭操作。部分初始化失败也会清理已打开的资源；一个关闭操作失败时，其他已注册资源仍会尝试关闭。

当前执行器仍限单用户、单进程。进程内锁与任务所有权没有替代分布式队列、租约、跨进程协调或团队鉴权；本轮没有开放多 worker 部署保证。

## 3. Sandbox 结果、审计与关闭

执行结果先持久化，关联研究事件随后单独写入。结果保存成功后，审计事件写入失败会记录稳定的警告，保留原有执行状态与输出，不把成功计算改写为执行失败。此类故障仍可能造成审计事件缺失，应结合持久执行记录和服务日志检查；业务结果本身的数据库写入失败仍需单独处理。

关闭时停止接受新执行，等待正在登记的提交完成注册，取消尚未结束的生产者，并等待所有持有任务收尾。即使数据库已显示终态，仍等待该生产者后续的审计与清理操作，再关闭执行器和数据库，避免资源过早释放。

Docker 的隔离配置、资源限制、无网络执行和固定镜像要求沿用 [Sandbox 文档](./SANDBOX.md)。本轮没有引入新的宿主执行入口。

## 4. 全局写入请求体限额

`MAX_REQUEST_BYTES` 默认 **`1048576` 字节（1 MiB）**，在 JSON 解析和字段校验之前检查请求体。覆盖 `/api`、`/a2a` 及其子路径下的 `POST`、`PUT`、`PATCH`，包括 A2A JSON-RPC 和 Sandbox 执行请求。

限额按实际接收的请求体字节累计，不能通过缺少 `Content-Length` 或分块传输绕过。它独立于 Sandbox 解码后的代码、输入和输出上限；JSON 字段校验通过仍需满足请求整体字节限制。

| 条件 | HTTP 状态 | 响应 `code` |
| --- | --- | --- |
| 声明或实际接收的请求体超过上限 | `413` | `request_body_too_large` |
| `Content-Encoding` 包含非 `identity` 编码 | `415` | `unsupported_content_encoding` |

未设置内容编码或使用 `identity` 可继续处理。GET、SSE 和 ASGI 生命周期消息直接沿用原有通道，不预缓冲事件流。请求在上传完整 body 前断开时，不进入后续 JSON 解析。

可在环境配置中调整上限：

```dotenv
MAX_REQUEST_BYTES=1048576
```

## 5. 验证与 CI

本轮本地完整回归 **234 项通过**。覆盖确认后 A2A 重试、迟到响应与终态、取消/恢复并发、创建提交窗口的断连与关闭、AG-UI 最终审计事件、Sandbox 审计故障、生产者关闭、请求体限额，以及真实 PostgreSQL、Docker 和双 HTTP 实例。

离线评测为 **9/9 场景、55/55 项期望匹配**。它使用固定夹具或脚本模型，未使用真实模型、嵌入、外部神经 Reranker 密钥，也未上传 LangSmith；真实研究质量与这些服务的运行效果仍需配置后验收。

GitHub Actions 保留 Python 3.13、uv 0.13.5 的离线 lint、格式、测试、评测与 JavaScript 语法检查，并新增独立集成任务：

- 使用 `pgvector/pgvector:pg17` 和一次性的 `signaldesk_ci` 测试数据库，与 Compose 的 PostgreSQL 镜像一致；预检启用 vector 扩展。
- 预拉固定的 `python:3.14-slim` 镜像，设置 `SIGNALDESK_TEST_DOCKER=1` 和指向该测试库的 `SIGNALDESK_TEST_POSTGRES_URL`。
- 真正执行 `tests/test_postgres_integration.py` 与 `tests/test_sandbox_docker.py`，使用测试凭据，清空模型和 LangSmith 密钥。
- 离线任务通过后，仅允许上游仓库的可信 push 或同仓库 PR 运行集成；fork PR 继续运行离线检查。权限为 `contents: read`，集成任务总超时为 20 分钟。

CI 配置已完成本地结构与命令检查，各次提交的云端实际结果见 [GitHub Actions](https://github.com/01jiyuge/signaldesk/actions/workflows/ci.yml)。

本地离线检查命令保持不变：

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
uv run signaldesk-eval
node --check src/signaldesk/static/app.js
```

运行真实集成前，应准备独立 PostgreSQL 测试库、pgvector 扩展权限、可用 Docker 和固定 Python 镜像，再设置上述两个测试环境变量并执行：

```bash

```
