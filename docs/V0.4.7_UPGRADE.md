# V0.4.7 · SQLite 离线备份与恢复

日期：**2026-10-23**。版本：**0.4.7**。本轮增加三个本地数据库的统一维护命令与协作进程锁。业务库包含项目、报告、快照和事件，checkpointer 保存图进度，Store 保存明确偏好及运行摘要；只备份业务库不能还原完整任务状态。

## 1. 使用命令

先停止所有使用这些数据库的服务、旧版本进程与外部写入工具。在项目目录执行：

```bash
uv sync --frozen --extra dev
mkdir -p data/backups
uv run signaldesk-db backup --output data/backups/before-upgrade
uv run signaldesk-db verify data/backups/before-upgrade
uv run signaldesk-db restore data/backups/before-upgrade --target-dir data/restored-before-upgrade
```

`backup` 从当前工作目录的 `.env` 与环境变量读取 `DATABASE_URL`、`CHECKPOINT_URL`、`MEMORY_URL`，要求三个角色均为已存在的本地 SQLite 文件。目标父目录必须存在，目标目录必须不存在；命令没有覆盖或 `--force` 选项。

`verify` 与 `restore` 不加载 `.env`，不依赖当前数据库设置，不初始化表或恢复任务。`restore` 校验后只发布到新目录，输出 `urls.database_url`、`urls.checkpoint_url`、`urls.memory_url`。检查后把这三条地址分别设置为上述环境变量，再启动服务；原库和当前配置不会被自动替换。

每条命令支持 `--timeout 60`，CLI 允许 **1–600 秒**的有限数值，默认 60 秒。成功向 stdout 输出 `{ "status": "ok", "command": ... }` JSON；维护失败向 stderr 输出 `{ "status": "error", "code": ..., "message": ... }`，退出码为 1；参数错误退出码为 2。错误不回显连接串、原始异常或密钥。

## 2. 备份内容与校验

备份目录只包含：

```text
manifest.json
business.sqlite3
checkpoints.sqlite3
memory.sqlite3
```

清单格式版本为 1，记录应用版本、生成时间，以及固定角色、文件名、字节数和 SHA-256。清单不收集 `.env`、源绝对路径、URL 或令牌。数据库本身包含项目原文、报告与记忆，备份应保存在私有位置，不提交到 GitHub。

复制使用 SQLite backup API，以只读连接读取已提交内容，包括尚未 checkpoint 的 WAL；不直接复制主 `.db` 文件。三个源文件在同一组协作锁下保持静止，逐个生成副本。副本切为 DELETE journal，关闭后执行完整 `integrity_check`、`foreign_key_check` 和哈希校验，生成不依赖 WAL/SHM 的独立文件。

`verify` 严格检查清单字段、版本、角色唯一性、固定文件名、大小、哈希与 SQLite 完整性；拒绝路径穿越、文件链接、额外文件和 WAL 文件头。校验不会把 WAL 归档作为活动数据库打开并生成旁路文件。哈希用于发现损坏和不一致，不是备份来源的数字签名。

## 3. 进程锁与路径身份

服务在构造资源前冻结配置副本，将三个 SQLite 路径统一为绝对规范路径。构造后改变工作目录、重定向原符号链接或修改传入的 Settings，不会让实际数据库和锁落在不同位置。三个 SQLite 适配器与维护命令使用相同解析规则。

服务在任何初始化或中断恢复之前，按稳定顺序为每个不同 SQLite 文件取得非阻塞独占锁，持有至后台任务、Store、checkpointer、Sandbox、检索器和业务库全部关闭。两个配置只共享一个数据库也会冲突；三个角色共用同一个文件时只取得一次锁。

锁文件为 `<数据库名>.signaldesk.lock`，权限 0600，退出后保留。文件存在不代表进程仍运行，操作系统锁才决定所有权；正常退出或进程被终止后可重新取得锁。**不要删除运行中服务的锁文件**，否则可能创建不同 inode 绕开原锁。锁冲突返回 `storage_busy`，应先停止另一个进程。

本轮本地锁及备份/恢复支持 Linux 和 macOS、本地文件系统。SQLite URI、URL 查询参数、含 `?` 的实际路径、硬链接和特殊文件不受支持。文件路径中的空格、中文、`#`、`@`、`%` 已纳入回归。PostgreSQL 服务路径保持可用；维护命令不备份 PostgreSQL 或混合后端，内存数据库也不作为备份源。

服务可以解析符号链接别名；`backup` 的源数据库须直接指向普通文件，最终文件符号链接会被拒绝。

这些锁只约束采用本协议的 SignalDesk 服务与命令，不阻止旧版服务、独立 Repository 调用或外部 SQLite 写入工具。维护前仍需停止所有写入者；网络文件系统和被外部程序同时修改的目录不在支持范围内。

## 4. 发布与失败处理

备份和恢复都先在目标同父目录创建私有临时目录，完成三个文件及清单的写入、同步和完整校验后，再发布整个目录。目录权限为 0700，数据库和清单为 0600。恢复时对复制后的文件再次校验，防止仅凭源预检就发布不一致内容。

同名 SignalDesk 发布命令由持久协作锁互斥，锁内再次检查目标不存在；已存在的目标一律拒绝。发布前失败仅清理本次创建的临时目录。进程被强制终止时可能留下 `.signaldesk-stage-*`，该目录不是已发布备份；确认无维护进程后可另行处理。

目录重命名成功后，若父目录同步失败，返回 **`publication_uncertain`**：产物已发布，但耐久性未确认。此时先对目标执行 `verify`，不要盲目重试、删除产物或覆盖原库。校验成功只说明当前可读字节完整，不代替硬件持久性保证。

本轮不提供跨三个已有文件的覆盖恢复；三次单文件替换不构成三库原子恢复。新目录恢复让原库始终可保留，检查成功后由使用者切换配置。没有自动数据库迁移或自动恢复后台任务。
